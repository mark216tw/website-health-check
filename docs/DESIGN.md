# 系統設計文件

## 1. 設計目標

### 1.1 主要目標

- 讓使用者以最少設定監控多個網站。
- 在 Android 背景限制下，提供可預期的自動檢查行為。
- 檢查結果與錯誤原因清楚可見。
- 發生異常與恢復時主動通知。
- 所有資料保存在本機，不需註冊或登入。
- 支援匯出紀錄，方便進一步分析。

### 1.2 非目標

- 取代專業的伺服器端監控服務（如 Prometheus、UptimeRobot）。
- 提供跨裝置同步或雲端備份。
- 保證分秒不差的檢查時間。
- 進行滲透測試、弱點掃描或 TLS 憑證完整度分析。
- 執行 JavaScript 或模擬瀏覽器渲染。

## 2. 使用情境

1. 使用者新增公司官網與 API 網址。
2. 設定週一至週五 09:00–18:00，每 30 分鐘檢查。
3. App 在允許時段自動檢查，記錄狀態與回應時間。
4. 網站連續失敗 3 次時發送通知。
5. 網站恢復時再發送一次恢復通知。
6. 使用者透過紀錄頁篩選失敗項目，匯出 CSV 分析。
7. 使用者可選擇淺色／深色模式，系統列同步變化。

## 6. 排程設計細節

### 6.1 資料欄位

- `daysOfWeek`：7 bits，bit 0 = 星期一，bit 6 = 星期日。
- `windowStartMinutes` / `windowEndMinutes`：0–1440 分鐘。
- `intervalMinutes`：最低 15。
- `lastCheckAt`：上次完成檢查的時間。

### 6.2 計算公式

```text
interval = max(intervalMinutes, 15)
target =
    now                                  if forceImmediate or lastCheckAt == null
    max(now, lastCheckAt + interval)     otherwise

next = 最早符合下列條件的時間：
        - 該日為啟用星期
        - target 落在 [windowStart, windowEnd)
        - 若 target 早於 windowStart，取 windowStart
        - 若 target 超過 windowEnd，跳至下一個時段
```

跨午夜條件：`windowEnd <= windowStart` 時，`windowEnd` 視為隔日。

### 6.3 邊界案例

| 情境 | 行為 |
|---|---|
| 從未檢查，現在在時段內 | 立即檢查 |
| 從未檢查，現在在時段外 | 下一個時段開始 |
| 上次檢查 + 間隔已過 | 立即補檢查 |
| 下次時間超過當日時段 | 順延到下一個啟用日時段 |
| 時段 23:00–01:00 | 視為跨午夜 |
| 開始時間等於結束時間 | 視為 24 小時 |
| 間隔小於 15 | 以 15 計算 |
| 未選擇任何星期 | 不排程（表單也會阻擋儲存） |

### 6.4 與 WorkManager 的搭配

- 每個網站一個 unique work。
- Worker 完成後以 `APPEND_OR_REPLACE` 建立下一次；重排於 `NonCancellable` 中執行。
- 修改設定、啟用、手動重新排程使用 `REPLACE`。
- 看門狗每 15 分鐘執行 reconciliation，補缺少或逾期的排程。
- 啟動／回到前景／時區變更時執行 reconciliation；逾期網站立即補檢查。
- 執行中的 Worker 不會被 reconciliation 中斷。
- 看門狗仍受 Doze／OEM 省電限制。

## 7. 網站狀態模型

| 狀態 | 條件 | 顏色 |
|---|---|---|
| 已停用 | `enabled = false` | 灰色 |
| 尚未檢查 | `lastSuccess = null` | 次要色 |
| 正常 | `lastSuccess = true` | 綠色 |
| 異常 | `lastSuccess = false` | 紅色 |
| 檢查中 | 使用者剛觸發立即檢查 | 主色 |

檢查中狀態不寫入資料庫，僅存在 ViewModel 記憶體：

- 開始：記錄 `startedAt` 並加入 `checkingIds`。
- 結束：收到資料庫更新且 `lastCheckAt >= startedAt`，或網站停用／刪除。
- 逾時：90 秒後強制移除，避免 Worker 異常時永久轉圈。

## 8. 通知狀態機

```text
正常 --失敗--> 失敗中 --達門檻--> 已通知異常
失敗中 --成功--> 正常（不通知）
已通知異常 --持續失敗--> 已通知異常（不重複）
已通知異常 --成功--> 發送恢復通知 --> 正常
```

`notifiedFailure` 儲存於網站資料，App 重啟後仍能正確判斷是否已通知。

| 類型 | 顯示文字 | 來源 |
|---|---|---|
| DNS | DNS 解析失敗 | UnknownHostException |
| TIMEOUT | 連線逾時 | SocketTimeoutException |
| TLS | TLS／憑證錯誤 | SSLException |
| NETWORK | 網路連線失敗 | 其他 IOException |
| STATUS | HTTP 狀態碼異常 | 狀態碼不在預期範圍 |
| KEYWORD | 內容未包含指定字串 | 字串比對失敗 |
| INVALID_URL | 網址格式錯誤 | IllegalArgumentException |
| OTHER | 其他錯誤 | 其他例外 |

## 10. 排序設計

| 選項 | 規則 |
|---|---|
| 新增時間（舊→新） | `createdAt` 升冪，再以 id |
| 新增時間（新→舊） | `createdAt` 降冪，再以 id 降冪 |
| 名稱（A→Z） | 名稱小寫升冪，再以建立時間 |
| 名稱（Z→A） | 名稱小寫降冪，再以建立時間 |
| 最近檢查（新→舊） | `lastCheckAt` 降冪，null 最後 |
| 最近檢查（舊→新） | `lastCheckAt` 升冪，null 最後 |
| 狀態（異常優先） | 異常 → 尚未檢查 → 正常 → 已停用，再以名稱 |
| 回應時間（慢→快） | `lastLatencyMs` 降冪，null 最後 |
| 回應時間（快→慢） | `lastLatencyMs` 升冪，null 最後 |

排序選擇以 `site_sort` 儲存，跨 App 重啟保留。

## 11. 重複網址設計

- 儲存前將網址正規化：
  - 補上 `https://`
  - 使用 OkHttp `HttpUrl` 轉為標準字串（主機小寫、預設連接埠、路徑格式）
- 與所有網站（含停用）比較。
- 編輯時排除自己的 id。
- 發現重複時顯示確認視窗，允許使用者仍要儲存。

## 12. 內容字串檢查

- 啟用後強制 GET。
- 只讀取前 1 MB，避免大檔案造成記憶體與流量問題。
- 使用 `String.contains`，區分大小寫。
- 只比對原始 HTTP 回應，不執行 JavaScript、不解析 DOM。
- 狀態碼不符合時優先回報 HTTP 狀態錯誤，不再進行內容比對。

## 13. 資料保留

- 預設保留 30 天。
- 清理時機：
  - App 啟動
  - 變更保留天數
  - 每次檢查完成
- 刪除條件：`checkedAt < now - retentionDays`。
- 網站刪除時，其檢查紀錄透過外鍵 CASCADE 刪除。

## 14. 顯示模式

- 使用 `ThemeMode` 列舉：`SYSTEM`、`LIGHT`、`DARK`。
- 儲存於 SharedPreferences。
- MainActivity 收集設定並傳入 `WebsiteCheckTheme`。
- 主題切換時重新套用 edge-to-edge 系統列樣式。

## 15. 設計取捨

| 決策 | 原因 | 代價 |
|---|---|---|
| WorkManager 而非前景服務 | 省電、無常駐通知 | Doze 下可能延遲 |
| 一次性工作自我重排 | 可精確表達星期／時段／間隔 | 比 PeriodicWorkRequest 複雜 |
| 相對上次檢查時間排程 | 符合「每 N 分鐘」直覺 | 檢查時間可能略為漂移 |
| 最低間隔 15 分鐘 | 降低電量與系統限制風險 | 無法設定更密集檢查 |
| 原始 HTML 字串比對 | 無需額外解析器、行為可預期 | 看不到 JavaScript 動態內容 |
| 前 1 MB 限制 | 控制記憶體與流量 | 大型頁面後段內容可能漏判 |
| 本機儲存、無帳號 | 隱私與簡單 | 無跨裝置同步 |
| 保留 500 筆畫面查詢 | 畫面效能穩定 | 更舊紀錄需匯出 CSV 查看 |
